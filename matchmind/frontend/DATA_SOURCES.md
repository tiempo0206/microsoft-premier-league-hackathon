# Match data accuracy and adoption status

Updated on 2026-10-26 against main `1113388`, including B's verified Wyscout package (PR #17) and C's offline comparisons/tuned synthetic proposal. The representative's policy is to prefer real data when it can support the platform, otherwise use a clearly identified synthetic fallback. The runtime remains synthetic; real data is used offline for comparison, not playable historical ingestion. A real model generating text does not make its input match a real match.

These are consistent **synthetic** statistics, not independently observed Premier League facts. Goal events determine score; shots are counted separately. Evidence positions do not establish off-ball movement or tactical causality.

Provenance: `data/extra/validated-demo/PROVENANCE.json`, match metadata, events and `expected.json`; original source `data/fixtures/PROVENANCE.json`. Contract 2.0.0 fixes `synthetic` to true and the frontend requires it.

## Offline calibration now measured

C chose calibration/comparison for this submission and deferred independent historical playback. From `matchmind`, run `.venv/bin/python -m evaluation.real_data_calibration --json`. A reran this offline on 2026-10-26 against `1113388` with zero model calls. The shared 300-second window has 96 real records versus 30 shipped synthetic events, 110 in the original dense proposal and 106 in the tuned proposal. The tuned profile matches this sample's indicative shot rate (8 per ten minutes); pass share and other gaps remain. Six of twelve comparisons exceed their declared tolerances. The tool's successful exit means it generated a report, not that all realism comparisons passed.

These are one historical excerpt's comparisons, not a league distribution, broad realism guarantee or proof that the tuned proposal is deployed. Shot classes and event vocabularies differ; duels/interruptions/loose-ball events have no direct 2.0.0 equivalents. The report refuses recovery/linkage, possession-control/trigger and pass-completion calculations where the source cannot support them. See [C's methodology and results](../evaluation/README.md) and `evaluation/real_data_calibration.py`. The current default fixture/runtime remains unchanged; the tuned generator profile is a separate proposal.

## Requirements before switching the public dataset

Track the cross-role work in [issue #15](https://github.com/tiempo0206/microsoft-premier-league-hackathon/issues/15). B's source delivery and C's offline comparison/tuned proposal are complete; default runtime ingestion has not changed. Any future independent historical replay requires C to version the frozen contract with A/B review and define initial state and provider mapping. A then consumes those agreed fields. No real input may be labelled synthetic to pass the existing validator.

For a future historical runtime, A needs reviewed semantics for source kind/provider/version/ID, match date and competition/season, home/away identity, initial clip score, attribution/license and any derivation/missing-data notice. These are review requirements, **not new API field names or an implemented alternate schema**. The current submission uses the chosen offline-comparison route, with the reference outside the playable catalogue. It does not claim that the shipped fixture was tuned or replaced.

The mapping must preserve the original period clocks, outcomes, own-goal handling, coordinates/attack direction and possession semantics. Missing facts remain unavailable. Derived possession estimates and heuristic detections must be labelled as derived; no generated recoveries, player motion or event positions may be inserted into a real match. Verify events against published metadata and reconcile full-match and clip statistics before public acceptance.

The [hackathon rules §4.7](https://github.com/microsoft/insidethegamehackathon/blob/main/OFFICIAL%20RULES.md#47-use-of-footage) require synthetic football-realistic data. C's current submission decision retains the synthetic runtime and uses the delivered real reference offline. A future historical mode or tuned runtime adoption still needs its own reviewed integration and submission-scope decision.
